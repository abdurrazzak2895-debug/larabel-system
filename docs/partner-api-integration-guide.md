# Partner Website API Integration Guide

**API version:** v1  
**Production API host:** `https://api.choice-pc-sv.xyz`  
**Integration type:** server-to-server, read-only availability lookup  
**Last verified:** 2026-10-22

This guide explains how another website can consume the Takamol availability API without installing Laravel, using the upstream Takamol credentials, or handling SVP bearer tokens.

## 1. What this API provides

The gateway exposes normalized availability data for:

- Occupations
- Active cities for a category
- Available exam dates
- Test centers
- Exam sessions, exam times, and available seats

The partner website only needs an API key generated by the Takamol admin panel. The Laravel server keeps the upstream agent session and credentials private.

The gateway does **not** expose login, OTP, candidate accounts, temporary holds, reservations, booking confirmation, payment, cancellation, or rescheduling endpoints. Do not build a booking-confirm flow against these lookup routes.

## 2. Choose the gateway

### Takamol gateway — recommended for the current booking catalogue

- Header: `X-Takamol-API-Key`
- Uses the server-side shared Takamol/T2Hub agent session
- Base path: `/api/external/takamol-availability/v1`
- Admin page: `/admin/takamol-api-access`

### SVP gateway — optional candidate-session catalogue

- Header: `X-Portal-API-Key`
- Uses an encrypted, administrator-selected candidate SVP session
- Base path: `/api/external/svp-availability/v1`
- Admin page: `/admin/external-api-access`

For a new partner website that needs the same occupation → city → date → center → session catalogue used by the Takamol booking UI, use the Takamol gateway.

## 3. Generate and protect an API key

A Super Admin with the required agency-management permission should:

1. Sign in to the Laravel admin panel.
2. Open **External Takamol API Access**.
3. Create a key name, optional expiry, and per-minute limit.
4. Copy the plaintext key immediately. It is shown only once.
5. Store it only in the partner website's server-side secret manager or environment variables.

Example server configuration:

```dotenv
TAKAMOL_API_BASE_URL=https://api.choice-pc-sv.xyz
TAKAMOL_API_KEY=replace_with_the_key_from_admin_panel
```

Never put the key in:

- Browser JavaScript
- HTML
- Mobile-app source code
- Query parameters
- Git commits
- Public logs
- Chat messages or screenshots

The API stores only a SHA-256 hash of the key. Revoke a key immediately if it is exposed. For rotation, issue a replacement first, deploy it, verify it, then revoke the old key.

## 4. Authentication and common headers

Every Takamol endpoint requires the key in this header:

```http
X-Takamol-API-Key: <server-side-api-key>
Accept: application/json
```

Example:

```bash
curl -G 'https://api.choice-pc-sv.xyz/api/external/takamol-availability/v1/occupations' \
  -H "X-Takamol-API-Key: ${TAKAMOL_API_KEY}" \
  -H 'Accept: application/json'
```

The key must be sent from the partner backend. A browser should call the partner backend, not this gateway directly.

## 5. Takamol endpoint reference

All endpoints are `GET` requests.

| Endpoint | Required query | Optional query | Purpose |
|---|---|---|---|
| `/api/external/takamol-availability/v1/occupations` | None | `search` | Occupation catalogue |
| `/api/external/takamol-availability/v1/cities` | `category_id` | None | Category-scoped active cities |
| `/api/external/takamol-availability/v1/dates` | `category_id`, `city` | None | Available dates for a city |
| `/api/external/takamol-availability/v1/centers` | None | `city` | Test-center catalogue, optionally filtered by city |
| `/api/external/takamol-availability/v1/sessions` | `category_id`, `city`, `exam_date` | `test_center_id` | Sessions, center data, exam time, and seats |

`exam_date` must use `YYYY-MM-DD`. Query parameters should be URL encoded.

## 6. Recommended lookup workflow

Use this order:

1. Load occupations and let the operator select an occupation/category.
2. Call `cities` with the selected `category_id`.
3. Call `dates` with the selected city.
4. Enable only dates returned by `dates`.
5. Call `centers` for the selected city if a center list is needed.
6. Call `sessions` for the selected date. Optionally pass `test_center_id` to narrow the result.
7. Display `available_seats` and `exam_time` from the session response.

The dates response is the source of truth for clickable dates. The center catalogue can contain more centers than currently have dates; do not treat the center list alone as proof of availability.

## 7. Request examples

### 7.1 Search occupations

```bash
curl -G 'https://api.choice-pc-sv.xyz/api/external/takamol-availability/v1/occupations' \
  -H "X-Takamol-API-Key: ${TAKAMOL_API_KEY}" \
  --data-urlencode 'search=Barber'
```

### 7.2 Load cities for a category

```bash
curl -G 'https://api.choice-pc-sv.xyz/api/external/takamol-availability/v1/cities' \
  -H "X-Takamol-API-Key: ${TAKAMOL_API_KEY}" \
  --data-urlencode 'category_id=50'
```

### 7.3 Load available dates

```bash
curl -G 'https://api.choice-pc-sv.xyz/api/external/takamol-availability/v1/dates' \
  -H "X-Takamol-API-Key: ${TAKAMOL_API_KEY}" \
  --data-urlencode 'category_id=50' \
  --data-urlencode 'city=Dhaka'
```

### 7.4 Load all centers in a city

```bash
curl -G 'https://api.choice-pc-sv.xyz/api/external/takamol-availability/v1/centers' \
  -H "X-Takamol-API-Key: ${TAKAMOL_API_KEY}" \
  --data-urlencode 'city=Dhaka'
```

Omit `city` to request the complete center catalogue.

### 7.5 Load sessions for a date

```bash
curl -G 'https://api.choice-pc-sv.xyz/api/external/takamol-availability/v1/sessions' \
  -H "X-Takamol-API-Key: ${TAKAMOL_API_KEY}" \
  --data-urlencode 'category_id=50' \
  --data-urlencode 'city=Dhaka' \
  --data-urlencode 'exam_date=2026-10-25'
```

### 7.6 Narrow sessions to one center

```bash
curl -G 'https://api.choice-pc-sv.xyz/api/external/takamol-availability/v1/sessions' \
  -H "X-Takamol-API-Key: ${TAKAMOL_API_KEY}" \
  --data-urlencode 'category_id=50' \
  --data-urlencode 'city=Dhaka' \
  --data-urlencode 'exam_date=2026-10-25' \
  --data-urlencode 'test_center_id=45'
```

## 8. Response format

Successful responses use this envelope:

```json
{
  "success": true,
  "data": {}
}
```

### Occupations

```json
{
  "success": true,
  "data": {
    "occupations": [
      {
        "id": "123",
        "name": "Barber",
        "category_id": "50"
      }
    ]
  }
}
```

Treat additional fields as forward-compatible. Use the occupation/category identifier returned by the API rather than hard-coding labels.

### Cities

```json
{
  "success": true,
  "data": {
    "category_id": "50",
    "cities": [
      { "id": "Dhaka", "name": "Dhaka" },
      { "id": "Rajshahi", "name": "Rajshahi" }
    ]
  }
}
```

### Dates

```json
{
  "success": true,
  "data": {
    "dates": [
      {
        "date": "2026-10-25",
        "city": "Dhaka",
        "test_center_date": true
      }
    ]
  }
}
```

Only dates returned by this endpoint should be enabled in the partner UI.

### Centers

```json
{
  "success": true,
  "data": {
    "sites": [
      {
        "id": "45",
        "name": "Bangladesh German TTC",
        "city": "Dhaka"
      }
    ]
  }
}
```

Depending on the provider data, a center may also expose aliases such as `site_id`, `center_id`, `site_name`, or `center_name`. Prefer the canonical `id` and `name` fields when present, but keep the parser tolerant of additional aliases.

### Sessions, exam time, and available seats

```json
{
  "success": true,
  "data": {
    "sessions": [
      {
        "session_id": "2221546",
        "exam_session_id": "2221546",
        "exam_date": "2026-10-25",
        "exam_time": "9:30 AM",
        "available_seats": 6,
        "site_id": "45",
        "site_city": "Dhaka",
        "center_name": "Bangladesh German TTC"
      }
    ],
    "exam_sessions": [],
    "sites": []
  }
}
```

The deployed gateway may include both `sessions` and the compatibility alias `exam_sessions`. Read `sessions` first and fall back to `exam_sessions` only if needed. A session with `available_seats: 0` should be displayed as unavailable and must not be treated as bookable.

Do not expose or persist encrypted/internal session identifiers in browser URLs. Use them only as opaque values on the partner backend if a future approved booking integration is added.

## 9. Error handling

| HTTP status | Meaning | Partner action |
|---:|---|---|
| 200 | Valid response | Read `success` and `data` |
| 401 | Missing, invalid, revoked, expired key, or unusable mapped SVP session | Stop and alert backend configuration; do not retry rapidly |
| 422 | Invalid or missing query parameter | Fix the request; do not retry unchanged |
| 429 | Per-key rate limit reached | Apply backoff and client-side caching |
| 502 | Upstream availability service temporarily failed | Retry with exponential backoff, then show a temporary-unavailable state |
| 5xx | Gateway/server failure | Retry safely for GET requests, then log a request correlation timestamp without logging the key |

Validation errors may use Laravel's standard JSON validation structure. Never display raw upstream exceptions to end users.

Example unauthorized response:

```json
{
  "success": false,
  "message": "The Takamol API key is invalid, revoked, or expired."
}
```

## 10. Backend integration examples

### Node.js

```js
const API_BASE = process.env.TAKAMOL_API_BASE_URL;
const API_KEY = process.env.TAKAMOL_API_KEY;

async function takamol(path, params = {}) {
  const url = new URL(`${API_BASE}${path}`);
  Object.entries(params).forEach(([key, value]) => {
    if (value !== undefined && value !== null && value !== '') {
      url.searchParams.set(key, value);
    }
  });

  const response = await fetch(url, {
    method: 'GET',
    headers: {
      Accept: 'application/json',
      'X-Takamol-API-Key': API_KEY,
    },
  });

  const body = await response.json().catch(() => ({}));
  if (!response.ok) {
    const error = new Error(body.message || `Takamol request failed: ${response.status}`);
    error.status = response.status;
    throw error;
  }
  return body;
}

const result = await takamol(
  '/api/external/takamol-availability/v1/sessions',
  { category_id: '50', city: 'Dhaka', exam_date: '2026-10-25' },
);
```

### PHP with Laravel HTTP client

```php
use Illuminate\Support\Facades\Http;

$response = Http::acceptJson()
    ->withHeaders(['X-Takamol-API-Key' => config('services.takamol.api_key')])
    ->get(config('services.takamol.base_url').'/api/external/takamol-availability/v1/sessions', [
        'category_id' => '50',
        'city' => 'Dhaka',
        'exam_date' => '2026-10-25',
    ]);

$response->throw();
$sessions = $response->json('data.sessions', []);
```

### Python

```python
import os
import requests

response = requests.get(
    os.environ['TAKAMOL_API_BASE_URL']
    + '/api/external/takamol-availability/v1/sessions',
    params={
        'category_id': '50',
        'city': 'Dhaka',
        'exam_date': '2026-10-25',
    },
    headers={
        'Accept': 'application/json',
        'X-Takamol-API-Key': os.environ['TAKAMOL_API_KEY'],
    },
    timeout=60,
)
response.raise_for_status()
sessions = response.json().get('data', {}).get('sessions', [])
```

## 11. Caching and performance

These are read-only GET lookups and are safe to cache briefly in the partner backend:

- Occupations: 10 minutes
- Cities: 5–10 minutes
- Centers: 5 minutes
- Dates: 30–90 seconds
- Sessions: 15–45 seconds

Do not cache errors for long periods. Do not cache a session response longer than the partner's acceptable seat-staleness window. After a user changes category or city, cancel or ignore stale in-flight requests so an older response cannot overwrite the current selection.

Recommended client sequence:

```text
occupation/category → cities → dates → centers → sessions
```

## 12. Optional SVP gateway contract

If the partner specifically needs a candidate-session-backed SVP catalogue, use the same endpoint names with this base path:

```text
/api/external/svp-availability/v1
```

Send:

```http
X-Portal-API-Key: <server-side-svp-api-key>
```

The endpoints are:

- `GET /occupations`
- `GET /cities?category_id=...`
- `GET /dates?category_id=...&city=...`
- `GET /centers?city=...&category_id=...`
- `GET /sessions?category_id=...&city=...&test_center_id=...&exam_date=YYYY-MM-DD`

The SVP key is mapped to an encrypted candidate session. The partner website must never receive or forward the upstream SVP bearer token. SVP keys and Takamol keys are different and are not interchangeable.

## 13. Production integration checklist

Before going live:

- [ ] Store the API key only in the partner backend secret store.
- [ ] Use HTTPS and validate the certificate normally.
- [ ] Do not call the gateway directly from browser JavaScript.
- [ ] Send `Accept: application/json`.
- [ ] URL-encode all query parameters.
- [ ] Use the category ID returned by the occupation catalogue.
- [ ] Enable only dates returned by the dates endpoint.
- [ ] Display seats and exam time from the sessions response.
- [ ] Handle 401, 422, 429, 502, and other 5xx responses.
- [ ] Add short-lived caching and request cancellation/race protection.
- [ ] Do not log the API key, upstream credentials, or opaque session tokens.
- [ ] Rotate and revoke keys through the admin panel.
- [ ] Test with a non-production or least-privileged consumer key where possible.

## 14. Capability boundary

This API is an availability/catalogue gateway only. It does not authorize the partner website to create a temporary seat hold, confirm a reservation, take payment, cancel a booking, reschedule an exam, or access candidate accounts. Those operations remain inside the Laravel application and require separate product, security, and authorization work.
